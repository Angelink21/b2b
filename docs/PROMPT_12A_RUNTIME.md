# 12A. Автообновление каталога из таблицы раз в ~5 минут

Перед запуском: `git add -A && git commit` (чистое дерево), затем `git switch -c feat/runtime-catalog`. Новый чат, Plan Mode → Agent, Grok 4.7, High, 256K, Fast выключен.
Команда: `Выполни промпт из @docs/PROMPT_12A_RUNTIME.md`.

```text
Задача: автообновление каталога из Google Таблицы примерно раз в 5 минут, без пересборки, cron, Deploy Hook и Apps Script.
Текущее состояние (проверено): каталог берётся статическим импортом catalog.generated.json в src/lib/catalog/index.ts (loadCatalog, кэш в памяти); таблица читается только в pnpm catalog:build (scripts/build-catalog.ts + src/lib/catalog/csv-source.ts); рантайм-чтения нет; 'use cache' есть только у года в Footer.tsx.
Источник: CATALOG_CSV_URL (значение в .env.local; в код, логи и отчёты не печатать). Фото (12B) не трогай. Правила: @.cursor/rules/20-next16-architecture.mdc, 40-catalog-data.mdc, 70-forms-security.mdc.

Сначала план (Plan Mode): список всех файлов, которые импортируют или используют данные каталога (серверные и клиентские), порядок миграции группами, риски. Жди «ок».

После «ок» работай маленькими шагами. На каждом шаге pnpm verify зелёный и остановка, чтобы я сделал коммит.
Шаг 1. Общая логика разбора и валидации в src/lib/catalog/pipeline.ts (build-catalog.ts и рантайм используют её). Поведение сборки не меняется.
Шаг 2. getCatalog(): async, 'use cache', cacheLife ≈ 5 минут (stale и revalidate около 300 с, expire около часа; проверь форму и поведение при ошибке ревалидации по докам Next.js 16.4). Внутри: скачать CSV (fetch, тайм-аут 20 с), разобрать и провалидировать, вернуть полный каталог, лёгкий индекс и серии. Результат кэшируемой функции только сериализуемый (простые объекты и массивы, без Map, Set и классов). Производные структуры (поиск по slug, по категории) строй вне кэша функциями поверх результата, мемоизируй через React cache().
Шаг 3. Миграция потребителей на getCatalog() группами: страницы каталога, категорий и карточек; линейка; мега-меню и подвал (счётчики); сравнение; sitemap, OG, JSON-LD; форма КП. Клиентский индекс передаётся пропсом с сервера, не импортом JSON. API src/lib/catalog становится асинхронным, тесты обновить.
Шаг 4. Защита. Снимок catalog.generated.json остаётся (на сборке из CATALOG_CSV_URL, иначе из data/products_clean.csv). Во время работы: не скачалось, пришёл HTML вместо CSV (нет доступа), заголовки не совпали с 22 колонками контракта, валидация упала или моделей меньше 80% от снимка → отдаётся предыдущий удачный результат или снимок, предупреждение в лог без персональных данных. Посетитель ошибок из-за таблицы не видит. На сборке те же ошибки роняют сборку (обход CATALOG_ALLOW_SHRINK=1).
Шаг 5. Статичность: generateStaticParams берёт модели из снимка (пререндер на сборке), новые модели из таблицы рендерятся при первом запросе и кэшируются, удалённые дают 404 (notFound()). Таблица маршрутов в `next build` остаётся static/partial prerender, без случайных ƒ. Route segment config, несовместимый с Cache Components, не использовать.
Шаг 6. Особенности Google Таблиц в разборе: BOM, \r\n, переводы строк в кавычках, пробелы по краям; число с запятой в поле с одним числом (6,25 → 6.25 с предупреждением), в списках запятая остаётся разделителем; «даты» вместо диапазонов («8-9» стало «8 сент.» или серийным числом) → ошибка с колонкой и моделью.
Шаг 7. /api/catalog-status (Bearer CATALOG_STATUS_SECRET, иначе 401): сборка (builtAt, modelCount, source) и рантайм (lastFetchAt, runtimeSource «sheet» или «snapshot», runtimeModelCount, lastErrors). Адрес таблицы не показывать.
Шаг 8. Тесты без сети: CSV-фикстуры (запятые, даты, лишняя и пропавшая колонка, HTML вместо CSV, потеря половины моделей), fallback на снимок, статичность маршрутов (по выводу сборки). docs/RUNBOOK.md: «правите таблицу → ~5 минут → проверка /api/catalog-status».
В конце: pnpm verify, pnpm e2e (0 упавших), pnpm build и pnpm start: страницы статичны, /api/catalog-status отвечает. Отчёт и стоп.
```

Как проверить обновление: подставь в `.env.local` адрес КОПИИ таблицы, `pnpm build`, `pnpm start`, поменяй в копии одну модель, подожди 6 минут, открой страницу модели два раза подряд (первое открытие может показать старое, второе новое).
