# Этап 12: каталог из Google Таблицы и фото из Cloudinary

Порядок: сначала закончи этап 10, потом 12B (фото), потом этап 11 (деплой), потом 12A (таблица). Один этап = один новый чат, Agent, Grok 4.7, High.
Если автоматизация таблицы пока не нужна, работает и простой путь: скачал CSV из таблицы, заменил `data/products_clean.csv`, `pnpm catalog:build`, коммит.

## Что подготовить самому

### Google Таблица
1. Заголовки колонок точно как в текущем CSV (22 колонки, см. `docs/DATA_CONTRACT.md`). Лист называется «Каталог».
2. Локаль таблицы: Файл → Настройки → Локаль → Соединённые Штаты. Иначе при экспорте десятичные точки могут стать запятыми.
3. Колонки с диапазонами и составными значениями (`Завантаження (кг)`, `Потужність (кВт)`, `Габарити`, `Рівень шуму`, `Робоча швидкість`, `Напруга живлення`) задай формат «Простой текст» ДО вставки данных (Формат → Число → Простой текст). Иначе «8-9» может превратиться в дату.
4. Выпадающие списки для `Тип обладнання` и `Тип нагріву` (Данные → Проверка данных), строка заголовков защищена (Данные → Защитить листы и диапазоны).
5. Публикация: Файл → Поделиться → Опубликовать в интернете → лист «Каталог» → формат CSV → Опубликовать. Скопируй ссылку (это `CATALOG_CSV_URL`). Ссылка публичная: в листе не должно быть ничего секретного. Опубликованный файл обновляется не мгновенно (обычно через несколько минут после правки).
6. Необязательно: колонка `image_id` для явного соответствия модели и фото.

### Cloudinary
1. Папка `fagor/models`.
2. Upload preset (Settings → Upload → Upload presets): Use filename as public ID = вкл, Unique filename = выкл, Overwrite = вкл, Folder = `fagor/models`. Иначе Cloudinary добавит случайный хвост к именам и сопоставление сломается.
3. Имя файла = значение колонки «Зображення» (например `LAP-08 TP2 E P.png`; в именах слэш `/` уже заменён на `_`).
4. Требования к фото: PNG или WebP с прозрачным фоном, вид строго спереди без перспективы, одинаковая дистанция съёмки, ширина от 2000px. Если фон белый, на светлой теме он гасится, на тёмной нужна вырезка.
5. Ключи (Dashboard → API Keys): cloud name, API key, API secret. Только в `.env.local` и в переменных Vercel. Никогда не отправляй их в чат и не коммить.

### Vercel (после этапа 11)
Переменные: `CATALOG_CSV_URL`, `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `CLOUDINARY_FOLDER`. Deploy Hook: Project Settings → Git → Deploy Hooks → создать для ветки `main`. URL хука секретный.

### Кнопка «Опублікувати» в таблице (Apps Script)
Расширения → Apps Script, вставь код, сохрани. Project Settings → Script properties → добавь `DEPLOY_HOOK_URL` с адресом хука (не клади его в ячейки). При первом запуске Google попросит разрешение.

```js
function onOpen() {
  SpreadsheetApp.getUi()
    .createMenu('Сайт')
    .addItem('Опублікувати зміни на сайт', 'publishSite')
    .addToUi();
}

function publishSite() {
  const ui = SpreadsheetApp.getUi();
  const url = PropertiesService.getScriptProperties().getProperty('DEPLOY_HOOK_URL');
  if (!url) { ui.alert('Не задано DEPLOY_HOOK_URL у властивостях скрипта.'); return; }
  const res = UrlFetchApp.fetch(url, { method: 'post', muteHttpExceptions: true });
  const code = res.getResponseCode();
  ui.alert(code >= 200 && code < 300
    ? 'Запит надіслано. Сайт оновиться за кілька хвилин.'
    : 'Помилка ' + code + '. Перевірте адресу хука.');
}
```

## ЭТАП 12B. Фото из Cloudinary (Agent)

```text
Контекст: @src/lib/images.ts, @docs/DATA_CONTRACT.md (imageKey), @.cursor/rules/20-next16-architecture.mdc, @.cursor/rules/40-catalog-data.mdc.
Цель: подключить фото из Cloudinary без файлов в репозитории. Где фото нет, остаётся силуэт.

Env (типизированно в src/env.ts, секреты только на сервере и при сборке): CLOUDINARY_CLOUD_NAME, CLOUDINARY_API_KEY, CLOUDINARY_API_SECRET, CLOUDINARY_FOLDER (по умолчанию fagor/models). Обнови .env.example. Без переменных сайт работает как сейчас.

1. scripts/sync-images.ts (pnpm images:sync, вызывается из catalog:build при наличии env): Cloudinary Admin API (resources по префиксу папки, пагинация) → public_id, width, height. Сопоставление с моделями по нормализованному ключу: imageKey без расширения, NFC, trim, без учёта регистра, пробелы/подчёркивания/дефисы равны; случайный хвост Cloudinary (_ и 6 символов) отбрасывай, только если иначе совпадения нет. Колонка image_id, если есть, главнее. Результат: src/data/images.generated.json (slug → { publicId, width, height }).
   Отчёт docs/IMAGES_REPORT.md: сколько моделей с фото, без фото (список), лишние файлы без модели, неоднозначные совпадения. Сборка падает только при неоднозначном совпадении.
2. getModelImage(product) читает images.generated.json и возвращает { url, width, height, alt, publicId } или null. alt: «{название}, {категория}».
3. Кастомный loader (src/lib/images/cloudinary-loader.ts): https://res.cloudinary.com/<cloud>/image/upload/f_auto,q_auto,c_limit,w_<w>/<publicId>, с корректным кодированием пробелов. Без новых зависимостей. Проверь по докам Next.js 16.4, нужна ли настройка remotePatterns при кастомном loader.
4. <ModelImage> везде (карточка, строки стартовых моделей, сравнение): aspect-ratio из реальных размеров (CLS 0), sizes по месту, priority только у LCP-картинки карточки. Нет фото или ошибка загрузки → силуэт. Светлая тема: белый фон гасится mix-blend-mode: multiply. Тёмная: фото на светлой подложке.
5. Линейка на главной: если фото есть у всех 8 моделей линейки, используй обрезку по содержимому (e_trim) и рисуй фото высотой по реальной высоте в мм × общий масштаб сцены; подпись кг остаётся по центру колонки. Если фото есть не у всех, все остаются силуэтами (напиши об этом в отчёте). В отчёт: отклонение соотношения сторон обрезанного фото от габаритов Ш/В больше 8% помечай предупреждением (скорее всего фото не фронтальное).
6. OG-картинки моделей: фото, если есть. JSON-LD Product: image только при наличии фото (абсолютный URL).
7. Тесты: unit на нормализацию и сопоставление (имена с «_», пробелами, хвостом), на loader (кодирование), на getModelImage без env.
Проверка: pnpm verify, pnpm e2e (0 упавших). Отчёт: сколько фото сопоставлено, список без фото. Затем стоп.
```

## ЭТАП 12A. Каталог из Google Таблицы (Agent, после этапа 11)

```text
Контекст: @scripts/build-catalog.ts, @docs/DATA_CONTRACT.md, @.cursor/rules/40-catalog-data.mdc, @docs/RUNBOOK.md.
Цель: каталог берётся из опубликованного CSV Google Таблицы (CATALOG_CSV_URL). Локальный CSV остаётся запасным вариантом и фикстурой тестов.

1. build-catalog.ts: при заданном CATALOG_CSV_URL скачивает CSV (fetch, тайм-аут 20 с, 3 ретрая), иначе читает data/products_clean.csv. Проверка заголовков по 22 колонкам контракта (порядок не важен, лишние колонки игнорируются, кроме image_id); при расхождении понятная ошибка с перечнем недостающих и лишних.
2. Особенности Google Таблиц: BOM, \r\n, переводы строк в кавычках, пробелы по краям; число с запятой в поле с одним числом (6,25 → 6.25 с предупреждением), но в списках напряжения и составных значениях запятая остаётся разделителем; значения, похожие на даты вместо диапазонов («8-9» стало «8 сент.» или серийным числом): ошибка «ячейка в колонке X у модели Y похожа на дату, задай формат “Простой текст”».
3. Защита: при любой ошибке валидации сборка падает (Vercel оставит прежнюю версию сайта). Число моделей меньше 80% от прошлого снимка (src/data/catalog.meta.json) → ошибка «каталог подозрительно уменьшился» (обход CATALOG_ALLOW_SHRINK=1).
4. docs/CATALOG_REPORT.md: добавь раздел «Что изменилось с прошлой сборки» (добавлены, удалены, изменены модели по названию).
5. Если название модели изменилось, URL меняется: храни src/data/slug-history.json и делай 301 со старых адресов на новые, где модель можно узнать (по imageKey или image_id). Удалённые модели отдают 404.
6. Тесты без сети: CSV-фикстуры («с запятыми», «с датами», «лишняя колонка», «нет колонки»), сетевой слой мокается.
7. docs/RUNBOOK.md, раздел «Как обновить каталог из таблицы»: правка листа → меню «Сайт → Опублікувати» → через 2–4 минуты сайт обновлён; что делать при красной сборке (лог Vercel, CATALOG_REPORT.md); как откатить (Promote прежнего деплоя).
Проверка: pnpm verify. Затем стоп.
```
